Corrections about how ccenv is versioned, installed and edited. Topic group; the git note is the loosest fit and is included because it is a standing user correction.

## Versioning

- One source of truth per version number (`version-must-have-one-source-of-truth`). `__version__` was hardcoded in each package's `__init__.py` while `pyproject.toml` held the real number; nobody bumped `__init__.py`. Drift: ccloop `--version` printed 0.10.1 vs installed dist 0.12.0; ccmemory 0.15.0 vs 0.17.0. Caught only because someone ran `ccloop --version` to confirm an install. A stale `--version` reads as "the install failed" and sends you debugging a deploy that succeeded. Fix: `from importlib.metadata import PackageNotFoundError, version as _dist_version`; `try: __version__ = _dist_version("<pkg>")` / `except PackageNotFoundError: __version__ = "0+unknown"` (stdlib from 3.8, safe under ccenvmcp's 3.9 floor, no dependency). Applied to ccloop, ccmemory and ccenvmcp in v0.20.1, though ccenvmcp had not drifted: the defect is the duplicated source, not the current value. `--version` now reports what is installed, not what is in the tree (they differ until reinstall; see `ccenv-installed-vs-source-version`).
- Tautological test: `from ccloop import __version__; assert __version__ in capsys.readouterr().out` imports the constant and asserts the command printed it; passes at any drift. When a test's expected value derives from the thing under test it verifies plumbing, not correctness. Replaced with: source must not hardcode a version (regex on `__init__.py`), and `__version__ == importlib.metadata.version(pkg)`.
- Generalization: same class as the ccmemory listing budget (estimator drifted from the serializer it modelled) and ccloop handoff staleness (hand-maintained doc going stale). Any value maintained by hand in a second place drifts silently. Audit question is "how many places carry this number", not "is it right".
- Bump the bundle, not just the component (`bump-top-level-bundle-version-not-just-subdir`). The user installs the top-level bundle, not subdirs. When a component under `/src/ccenv` (ccloop/, ccmemory/, ccusage/, ccteam/, ...) changes, bump the component `pyproject.toml`, `/src/ccenv/VERSION`, and add one `/src/ccenv/CHANGELOG.md` entry citing the component version (e.g. "ccloop v0.5.1: ..."). A component bump alone leaves what ships unversioned. User corrected the omission repeatedly ("you keep doing this").
- One version per piece of work — "mpath", "DRBD", "the installer" — not per session and not per defect, fix or test failure found during it (bundle v0.38.2). Before the first source change, read the top `CHANGELOG.md` entry, which names the open version and the work: a change that is part of that work joins it, even in a new session and even when it fixes a newly found bug; only different work bumps, immediately before the change, with the entry written at the bump naming the work. A write to `.ccmemory/` is not a source change. Number moves within an open version only to raise size (patch -> minor -> major), never to add a step. Commit, push, install or the owner saying so closes the open version; the next change opens a new one. Example: 0.36.0 installed partway through a session, so the installer fix after it shipped as 0.36.1.
- History of the boundary: old note said "after editing any component, do BOTH bumps in the same change", plus the old CLAUDE.md line "the version is revved as part of the change" -> seven bumps in one bug-fixing session before any release. The 2026-09-19 replacement, once per session, bumped once per ccloop context window: 0.90.31 -> 0.90.122 in twelve days. v0.38.1 "once per entry, naming the problem" let an mxfs session name an entry for one hang, find a second during the same 16-node mpath testing, and open 0.90.124 beside 0.90.123. User: "You're only supposed to bump the version one time for each thing you're working on ... Even if you use 300 sessions, that's one version." Rejected: commit-based boundary (some projects never committed; CHANGELOG entry works everywhere); owner-only closing ("We want less hand holding instead of more."); bumping at release (Claude cannot see a release, so an install outside Claude would ship changed code under an already-released number; bumping before the first change makes the number new before any install can happen).

## Installer constraints

- `install.sh` (ccenv's or any project's) must never write into the source tree, e.g. a `RELEASED` marker beside `VERSION` (`install-never-writes-to-source-tree`). User: "NO NO AND NO! app user or NO user should be able 'write' to this dir!! ... remember some users git clone trader then ./install.sh". The user codes as `steve` and installs as the application user; `~/.config/ccenv/installed-version` lives in the installing user's home, invisible to a session as `steve`. Other users install from their own `git clone`. An install is never observed by this tree or session, so Claude cannot detect a release; anything needed "at release" must happen before it (hence the up-front bump; see `bump-top-level-bundle-version-not-just-subdir`).
- No venv per component (`no-per-component-venvs`). Old ccloop README pattern (`python3 -m venv ~/.venvs/ccloop && pip install .` plus PATH symlink) is wrong. User: "we'd have a venv for EACH component of this repo?" Standard for a manual single-component install: `pip3 install --user .`, `pipx install .` as PEP 668 fallback. Five venvs = 5x disk for shared deps (mcp, anyio, pydantic), five symlink chains, inconsistent layouts, no needed isolation (same user, same `claude` CLI). The bundle `install.sh` (v0.4.1 nuance) installs all five components into ONE shared `--user` site so the `ccenvmcp` shim imports across ccmemory/ccusage/ccteam; pipx per-app venvs would break that, so do not convert it. On PEP 668 distros `--user` fails with `error: externally-managed-environment` and `set -e` aborts; install.sh probes for the `EXTERNALLY-MANAGED` marker (`sysconfig.get_path("stdlib")`) and, only when present AND pip supports it, exports `PIP_BREAK_SYSTEM_PACKAGES=1` for its subshell, covering every `pip install --user` (safe: everything lands in `~/.local`, never system site-packages). Manual unblock: `PIP_BREAK_SYSTEM_PACKAGES=1 ./install.sh`. Never write per-component venv recipes. See `shared-userbase-compiled-dep-abi-mismatch`, `pythonuserbase-in-zshenv`.
- `~/.claude/CLAUDE.md` ownership (`install-claude-md-component-owned`), set 2026-06-13 at the user's explicit direction. Top-level `install.sh` assembles ONLY the base (bundled `CLAUDE.md` plus user/system overlay blocks) inside `# [CCENV MANAGED]` ... `# [/CCENV MANAGED]`, FIRST, before any component installer (`assemble_ccenv_base_claude_md`); on re-run an awk strips the old managed block, regenerates it, preserves everything outside (idempotent, no backup churn). Each component installer appends its own marker-delimited idempotent section after it (e.g. `ccproject/install.sh` step 4 manages its `# [AWARENESS PROTOCOL]` from its own `global-claude-md-snippet.md`). Top level never reaches into component content. `CCPROJECT_SKIP_GLOBAL_CLAUDE_MD` was removed; do not reintroduce it or any skip coupling. Old design: top level pulled `ccproject/global-claude-md-snippet.md`, ran ccproject early with a SKIP gate, assembled the global file dead-last (line ~472) while ccproject consumed it at ~293 -> false "Global CLAUDE.md missing awareness protocol" verify failure. User: "submodules can install/update global CLAUDE.md as they wish ... installer should not install submodule CLAUDE.md changes." A new component needing global content gets its own self-install in its own installer. Load-bearing structure, like `mcp-heal-stale-command-pattern`; do not "simplify" it away.

## Git

- Never run `git` without explicit direction, any subcommand including read-only `status`, `diff`, `log`, `reflog` (`no-git-checkout-to-undo-own-edits`). "If you find yourself about to run `git`, STOP and ask the user what they want instead." Two violations: (1) undoing your own edits with `git checkout -- <file>` / `git restore` — use Edit/Write to restore content, or ask if you lack the prior text; the tree is shared state and checkout could wipe the user's uncommitted work ("it only affected my changes this time" is luck). (2) "Read-only verification" — verify file state with Read, grep, wc, find; if you need to know what is uncommitted, ask. Why strict: git is too blunt and side-effecting (index state, pagers, hooks, lockfiles); the bright line makes the ban safe to rely on, any carve-out invites the next ambiguous case. Implicit permission exists ("commit and push" allows the commit pipeline; "what's the git status" allows `git status`) but must come from the user's words, not inference. When in doubt, ask first, run never.
