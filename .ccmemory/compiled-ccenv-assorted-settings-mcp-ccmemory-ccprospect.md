## Claude Code settings and attribution

[[commit-attribution-is-two-controls]]: Claude Code appends two things to commit messages: `Co-Authored-By: Claude … <noreply@anthropic.com>` (governed by `includeCoAuthoredBy`) and `Claude-Session: https://claude.ai/code/session_…` (governed by `attribution.sessionUrl`, **defaults true**). `includeCoAuthoredBy: false` alone removes only the first; verified live 2026-09-10, both vanished only after `attribution.sessionUrl: false`. The session URL matters: it writes a session identifier into git history permanently and pushes it to the remote.
- Key name trap: `coAuthoredBy` (blogs, a web search summary call it "the modern key") is rejected by CLI 2.1.267: `Settings validation failed:` / `- : Unrecognized field: coAuthoredBy`. The Edit tool validates settings.json against the schema so it fails loudly. Schema is embedded in the binary at `~/.local/share/claude/versions/<ver>`, readable via `grep -ao "Claude-Session.\{0,60\}"`. `includeCoAuthoredBy` is marked deprecated yet is the only working key.
- Both live in `~/.claude/settings.json`. ccenv v0.32.0's `settings` step seeds four keys: `includeCoAuthoredBy: false`, `attribution.commit: ""`, `attribution.pr: ""`, `attribution.sessionUrl: false`, per sub-key so a deliberately-set trailer survives.
- Gotcha: never grep the ~100MB ELF with a greedy fixed-width lookbehind like `grep -ao ".\{700\}sessionUrl"`; it backtracks catastrophically. Anchor on the literal, take trailing context.

## CLAUDE.md and agents

[[repo-claude-md-is-managed-block-source]]: `assemble_ccenv_base_claude_md()` in install.sh (runs FIRST) rebuilds the `# [CCENV MANAGED]` region of `~/.claude/CLAUDE.md` each install: marker header -> verbatim `cat "$SCRIPT_DIR/CLAUDE.md"` -> overlay blocks -> closing marker. Content outside (e.g. `[AWARENESS PROTOCOL]`) is preserved. A direct edit inside the managed region survives only until the next install, so policy changes must ALSO land in `/src/ccenv/CLAUDE.md` (doubles as the repo's project instructions). Keep byte-identical: install.sh `cmp`s the assembled result against the installed file and no-ops when equal; verify by extracting the region between markers, dropping the 2 header-comment lines, diffing against the repo file. Precedent v0.13.3: the temp-file rule was edited in place in `~/.claude/CLAUDE.md`, later back-ported, bundle VERSION 0.13.2 -> 0.13.3, CHANGELOG + docs/install.md entries. Related `install-claude-md-component-owned`.

[[shipped-agents-embed-no-rules]]: ccenv v0.31.0 added to RULE FOUR that subagents inherit CLAUDE.md as of SESSION START (and `.claude/agents/*.md` registered then), so any rule a delegated task could violate must be embedded verbatim in the agent definition. ## Quota and cost

[[quota-two-weekly-buckets-and-context-weighting]] (measured from `/usage` and the 2.1.239 binary, 2026-08-22): session (5-hour) 15%, week all models 19%, **week (Fable) 25%**. CLI tracks six windows (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`, `overage`) via `GET /api/oauth/usage` (`fetchUtilization`).
- A sonnet subagent request cannot debit the Fable bucket (settles the delegation premise). Transfer, not freebie: Fable request debits both buckets, sonnet only all-models; delegation pays until all-models binds; at measured mix Fable binds (25% vs 19%).
- `get_context_usage`/statusline expose only `five_hour` and `seven_day`; per-model windows never reach them, so the loop's meter cannot see the exhausting bucket. Use `/usage`.
- +50% weekly-limits promo ran through 2026-08-31; do not calibrate on headroom from it.
- Cost is context-weighted: `/usage` says "89% of your usage was at >150k context. Longer sessions are more expensive even when cached." The mxfs cost-audit "~4,430 Fable requests/week" and request-count shares are proxies under one context profile; reject "every request costs the same". Delegation's real mechanism: grind output never enters the parent context, lowering context growth per request and extending work span inside the 500k cutoff.
- Full write-up `/src/ccenv/docs/context-economics.md` (verified hook mechanics: gate subagent pass-through on `agent_id` not `agent_type`; `PreToolUse` supports non-blocking `additionalContext`; a denied tool call has already cost its request).

## ccloop handoff and CLI

[[handoff-docs-must-be-freshness-stamped]] (SUPERSEDED by `never-make-sessions-maintain-handoff-docs`): ccenv v0.21.0 deleted the handoff module, its two `CCLOOP_HANDOFF_*` env vars, the freshness/STALE machinery and the prompt instruction to maintain a handoff doc under `<project>/.ccloop/`. The filename is deliberately not written down anywhere in the ccenv tree (a session that reads it goes looking). The 0.20.0 reasoning asked how to make a model-maintained handoff trustworthy; the answer was to have none. ccloop names the transcript in the prompt (`runner.prior_session_block`). User: "cost me millions in tokens." Durable parts: a doc the outgoing model must remember to update stops being updated (mxfs `state.md` 7 days stale across 36 ccloop runs while `state.sh` ran fresh; hence `state.py` is a computed hook); a stale hand-written doc is byte-identical to a fresh one, only mtime differs; render a problem INTO the block, never swallow it; audit every scraper for a cap (`files_edited` capped at 60; `last_text` caps at 4,000 chars, hitting it every session proves it was never a summary); `Last 20 bash commands` (465-803 tok, a third of the resume) stays cut; `summarize()` runs in the runner AFTER a session exits and relay is event-driven on the wall event (the token cutoff is only an early-relay knob). Dead: tiering rules, mtime freshness check, STALE marker, and the "1,284 tok (no handoff) -> 396 (fresh handoff)" result (priced only the prompt, not output tokens spent rewriting the file).

[[ccloop-cli-flags-thread-as-params]] (from `--model`, ccloop 0.9.0 / bundle 0.5.0): runtime config is env-driven (`_config()` reads `CCLOOP_*`) but CLI flags thread as keyword params `cli.main -> runner.cmd_run / cmd_resume -> runner.loop(..., model=None)`; `loop()` does `cfg = _config(); if model: cfg["model"] = model` (flag beats `CCLOOP_MODEL`).
Recipe for the next value flag (e.g. `--effort`): (1) `cli.py` `_extract_value_flag(argv, flag, what)` handles `--flag=V` and `--flag V`, last wins, missing-value error; `_extract_cutoff`/`_extract_model` wrap it and add validation (`--model` rejects empty/whitespace so `--model=` does not no-op via the falsy check in `_build_command`). (2) Thread through BOTH `cmd_run` and `cmd_resume`. (3) Update USAGE (Options + env var line "(--x flag wins over this)"). (4) Per-invocation like the env var; a resume does not remember the model, unlike `--cutoff`, persisted in `<run-dir>/cutoff` because guard/keepgoing hooks in other processes read it.
Testing: `tests/fake_claude.py` honors `FAKE_ARGS_FILE` (appends each argv as a JSON line); assert e.g. `CCLOOP_MODEL=sonnet` + `model="opus"` gives `argv[argv.index("--model")+1] == "opus"`. cli parse tests stub `runner.cmd_run`/`cmd_resume` (`_stub_run`/`_stub_resume` in test_cli.py), keep signatures in sync. Never write a seam test whose fake reimplements the override logic.

## ccmemory listing budget

[[list-budget-must-trim-every-tier]] (ccmemory 0.19.0): `memory_list` on mxfs (1,848 memories) shipped ~14.9k tokens against a 6,000 budget while `memory_stats` said 10,490, listing zero project notes and zero compiled articles (180 entries, all reference/feedback/user), paid every session and every relay. Four defects: (1) `Store.list_all` seeded `spent` with the full always-listed set and trimmed only the remainder, so the loop broke on the first project note; (2) `reference` was in `ALWAYS_LIST_TYPES` while `compile._select` ingested only `type='project'`, so nothing could ever retire a reference memory (write-only type); (3) `compiled-` articles competed with raw notes on mtime alone, 2 of 132 listed, while folding retired 1,494 notes; (4) `_entry_tokens` modelled `name+description+30` but the server shipped `json.dumps(indent=2)`, under-counting 1.42x and `memory_stats` inherited it. Plus `count_backlog` counted all types while only `project` was actionable: mxfs backlog floor 144 vs threshold 20, so the nudge could not be silenced by compacting.
- Invariants: a budget must be able to trim every tier including the first; keep `ALWAYS_LIST_TYPES` small, now `("user","feedback")` (BM25 search reaches reference); `ALWAYS_LIST_TYPES` and `compile.COMPILABLE_TYPES` must stay complementary (`test_compilable_and_always_listed_types_are_complementary`); an unsilenceable alarm is broken, count backlog only over what compile can ingest; estimator and serializer drift silently (`test_entry_tokens_tracks_real_wire_size`).
- Method: do not trust self-reported cost: `memory_stats.list_tokens_actual` 10,490 vs `len(json.dumps(payload))` 14,921. Probes `tests/measure_list_payload.py` and `tests/simulate_list_policy.py` (opens `index.db` `mode=ro`, simulates policy against real stores; surfaced defect 3).
- Cleared: 33 mxfs rows have frontmatter `name:` differing from filename (legacy, e.g. `feedback_commits.md` -> `name: Commits only when work is done/working`); index keys on frontmatter name and stores `path`, so `memory_get` resolves; 0 dead paths, 0 unindexed files.

## MCP

[[mcp-alwaysload-blocks-startup]]: `alwaysLoad` REMOVED in ccenv v0.13.2 (install.sh set `alwaysLoad: true` on ccmemory from v0.6.0; `strip_always_load()` now deletes it).
- Correction 1 (2026-07-24, recorded, not acted on): decompiled 2.1.219: `o = !su(process.env.MCP_CONNECTION_NONBLOCKING)`; `alwaysLoad === true` configs form tier "regular-required" and others "regular"; `Vyl(false, ...)` for the required tier is always blocking but bounded: `s = GVu()` = `MCP_CONNECT_TIMEOUT_MS`, default 5000; `awaitEachWithDeadline`; on expiry logs `[MCP] ${r}: ${c}/${i.length} not ready after ${s}ms — proceeding; background connection continues`. Deadline is per tier, shared; session starts anyway, so it never guaranteed registration.
- Correction 2 (2026-07-25, forced removal): atrader@clyde, Claude Code driving `google/gemma-4-26B-A4B-it` via OpenAI-compatible proxy (`chatcmpl-` tool_use_ids), 172 transcripts 2026-06-29 to 2026-07-25: broker/journal/scheduler/searxng (alwaysLoad unset) 353-495 successful calls each; ccusage (unset) used in 16 sessions, 0 rejections; **ccmemory (true): 0 successful memory_list ever**, 122 transcripts with `No such tool available`. ccusage is the control (same bundle, installer, box, proxy, session). Not deferral: no deferred-tool reminder named ccmemory tools; server healthy (`claude mcp list` Connected, handshake 0.18s, SessionStart hook fired in all 5 newest transcripts), which is why the model knew `mcp__ccmemory__memory_list` from injected prose.
- Still true: no hook can gate on MCP status (SessionStart hooks finish BEFORE the init event reporting `mcp_servers`; no post-connect hook phase, anthropics/claude-code#26112; scheduled/Remote Trigger sessions miss the deferred tool list, #41778). No load order (both tiers in one `Promise.all`; `~/.claude.json` key order irrelevant; "sentinel server that loads last" not implementable). The model can enumerate its own MCP surface from its tool list (eager as functions, deferred named in a system-reminder; split `mcp__<server>__<tool>` on `__`); `claude mcp list` is NOT in-session truth (spawns a second copy of every server). Enumeration cannot detect its own incompleteness; diff against a hardcoded expected set. No `claude mcp add` flag for it and `get`/`list` do not surface it: read `~/.claude.json`, rewrite via `claude mcp remove -s user <name>` + `claude mcp add-json -s user <name> '<entry>'` (add-json will not overwrite); prefer over `json.dump` of the 256KB file.
- Lesson: a memory recording "this mechanism does not do what its name says" is a finding to act on; Correction 1 sat unused a day while the predicted symptom was live and the diagnosis was re-derived badly twice.

[[prescribed-remedy-must-not-assume-its-own-tool-exists]] (ccmemory v0.13.0 -> v0.13.1): `SESSION_PROTOCOL` (injected by the SessionStart hook) v0.13.0 said for a missing `memory_list`: "Call `ToolSearch("select:mcp__ccmemory__memory_list")` once to try to pull in a late-connecting server." `ToolSearch` exists only when tool-search is enabled; on a gemma-4-26B session the model looked for `ToolSearch`, re-read its list, then ran a `Bash` call whose body was its own reasoning pasted as `#` comments. v0.13.0 still closed the silent-failure hole (a no-ccmemory session reads like a project with no memory); the regression was "silently wrong" -> "visibly stuck", better not right. Rule for injected "call tool X": (1) gate "IF, and only if, X is in your tool list"; (2) say absence is NORMAL and to SKIP, not hunt; (3) forbid the shell fallback by name (nothing in bash registers an MCP tool); (4) make the terminal state reachable from EVERY branch (v0.13.0's "If still unavailable after that, STOP" hung off the ToolSearch branch). Write for the least capable model that will read it, including `instenv.prompt` fan-outs.

[[ccenvmcp-stdlib-mcp-shim]] (2026-06-13): `ccenvmcp/` is a ~250-line stdlib-only Python 3.9+ FastMCP-compatible shim; every release of the official `mcp` SDK requires >=3.10, locking out Debian 11 / Raspberry Pi OS, RHEL/Alma/Rocky 9, Ubuntu 20.04. It was the ONLY hard 3.9 blocker (`nats-py` >=3.7, `watchfiles>=0.21` has a 3.9 abi3 build, all packages use `from __future__ import annotations`). API: `from ccenvmcp import FastMCP`; `FastMCP(name, instructions=...)`, `@app.tool()` on sync or async, `@app.tool(name=, description=, schema=)`, `app.run()`, `await app.run_stdio_async()`; newline-delimited JSON-RPC 2.0 over stdio (initialize, notifications/initialized, tools/list, tools/call, ping). 3.9 pitfall (`ccenvmcp/ccenvmcp/transport.py`): do not call `typing.get_type_hints()` (hints are strings like `"int | None"` that raise TypeError on 3.9); the shim parses annotation text (`_token_to_schema`: `X | None`, `Optional[X]`, `list[str]`); tests `ccenvmcp/tests/test_transport.py`. Consumers: ccmemory (low-level, 5 tools, explicit `schema=` to keep the `memory_write` `type` enum; `serve()` split into `build_app()` + `serve()`), ccusage (2 sync tools), ccteam (9 async tools, `instructions=`); `mcp` removed from deps, requires-python >=3.9; ccmemory 0.7.0, ccusage 0.2.0, ccteam 0.3.0. ccenvmcp is installed FIRST by install.sh and intentionally NOT a declared dependency (installs from local source, a declared dep would trigger a failing PyPI lookup). See `ccenvmcp/docs/mcp.md`, `ccmemory-debian-build-unknown-install-layout`, `no-per-component-venvs`.
