# ccenv assorted: CLAUDE.md, settings, agents, injected prompt text

Assorted group; notes share only that they concern what ccenv writes into Claude Code's settings, CLAUDE.md, agent definitions and injected prompts.

## Commit attribution is two controls (`commit-attribution-is-two-controls`)
- Claude Code appends two things to commit messages: `Co-Authored-By: Claude ... <noreply@anthropic.com>` (governed by `includeCoAuthoredBy`) and `Claude-Session: https://claude.ai/code/session_...` (governed by `attribution.sessionUrl`, which DEFAULTS true). `includeCoAuthoredBy: false` alone removes only the first; verified live 2026-09-10: the injected attribution reminder dropped the co-author line and kept `Claude-Session:` until `attribution.sessionUrl: false` was added. The session URL matters most: it writes a session identifier into git history permanently and pushes it to the remote.
- Key trap: `coAuthoredBy` (no `include`) is recommended by blog posts and a web search summary as "the modern key"; CLI 2.1.267 rejects it: `Settings validation failed: - : Unrecognized field: coAuthoredBy`. The Edit tool validates settings.json against the CLI schema so it fails loudly; don't trust the web. Schema is embedded in the binary at `~/.local/share/claude/versions/<ver>`; read with `grep -ao "Claude-Session.\{0,60\}"`. `includeCoAuthoredBy` is marked deprecated yet is the only key that works.
- Both live in `~/.claude/settings.json`. ccenv v0.32.0's `settings` step seeds four keys per sub-key: `includeCoAuthoredBy: false`, `attribution.commit: ""`, `attribution.pr: ""`, `attribution.sessionUrl: false`; a deliberately-set trailer survives.
- Search gotcha: never grep the ~100MB ELF with a greedy fixed-width lookbehind like `grep -ao ".\{700\}sessionUrl"`; it backtracks catastrophically and never returns. Anchor on the literal and take trailing context.

## Repo CLAUDE.md is the managed-block source (`repo-claude-md-is-managed-block-source`)
- `assemble_ccenv_base_claude_md()` in install.sh (runs FIRST) rebuilds the `# [CCENV MANAGED]` region of `~/.claude/CLAUDE.md` each install: marker header, verbatim `cat "$SCRIPT_DIR/CLAUDE.md"`, overlay blocks, closing marker. Content outside markers (e.g. `[AWARENESS PROTOCOL]`) preserved; the region is fully replaced.
- So an edit made inside the managed region survives only until the next install; every standing-order change must ALSO land in `/src/ccenv/CLAUDE.md` (also this repo's project instructions). Keep byte-identical: install.sh `cmp`s the assembled result against the installed file and no-ops when equal. Verify: extract the region between markers, drop the 2 header-comment lines, diff against the repo file.
- Precedent v0.13.3: the temp-file rule ("test scripts -> project `tests/`, /tmp only for true one-shots") was edited in place in `~/.claude/CLAUDE.md`; a later session back-ported it, bumped VERSION 0.13.2 -> 0.13.3, added CHANGELOG + docs/install.md entries. Related `install-claude-md-component-owned`.

## Shipped agents embed no rules (`shipped-agents-embed-no-rules`)
- ccenv v0.31.0 added a RULE FOUR bullet: subagents inherit CLAUDE.md as of SESSION START (`.claude/agents/*.md` also registered then), so any rule a delegated task could violate must be embedded verbatim in the agent definition. None of the four definitions in `/src/ccenv/agents/` does: `grind.md` (Bash/Read/Grep/Glob, model sonnet; rules only about reporting discipline: raw evidence, never silently truncate, batch aggressively; nothing on git ban, `find /` ban, `rm` shape, `python3`; highest risk, a pure shell runner), `scout.md`, `miner.md`, `memory-compactor.md` (narrower blast radius).
- Not broken in practice (inheritance covers pre-session rules) but breaks quietly for a rule authored mid-session. Rules a delegated task can plausibly violate: git ban (RULE TWO), `find /` ban (overlay already restates it for subagents: "This applies to subagents too — do not delegate a `find /` you are not allowed to run yourself"), permission-prompt/`rm` shape (SEVENTEEN), `python3` (SIXTEEN), scripts-not-in-/tmp (FIVE).
- Not done: the user's v0.31.0 instruction was to add the two audited items and nothing adjacent, so the gap was reported, not fixed.

## Handoff docs: superseded, durable half kept (`handoff-docs-must-be-freshness-stamped`)
- ccenv v0.21.0 deleted the handoff module, its two `CCLOOP_HANDOFF_*` env vars, freshness/STALE machinery and the prompt instruction to maintain a handoff doc under `<project>/.ccloop/`. Superseded by `never-make-sessions-maintain-handoff-docs`. The filename is deliberately not written anywhere in the ccenv tree (a session reading it goes looking). The 0.20.0 question "how do we make a model-maintained handoff trustworthy" had the answer "don't have one": the per-session transcript is complete, free and can't go stale; ccloop names it in the prompt (`runner.prior_session_block`). User: "cost me millions in tokens."
- Still true: a doc the outgoing model must remember to update stops being updated (mxfs `state.md` 7 days stale across 36 ccloop runs while `state.sh` ran fresh every session; why `state.py` is a computed hook). A stale hand-written doc is byte-identical to a fresh one; only mtime separates them. Render a problem INTO the block, never swallow it (`state.py`). Audit every scraper for a cap: `files_edited` was the only unbounded one, capped at 60; `last_text` caps at 4,000 chars and hitting it every session proves it was never a summary. `Last 20 bash commands` (465-803 tok, a third of the resume) cut in 0.20.0, stays cut. `summarize()` runs in the runner AFTER a session exits; relay is event-driven on the wall event; no "cutoff hook" generates the resume (the token cutoff is only an early-relay knob).
- Dead with 0.21.0: tiering rules, mtime-vs-session-start freshness check, STALE marker, and the "1,284 tok (no handoff) -> 396 (fresh handoff)" result (priced only the prompt, never the output tokens spent rewriting the file all run).

## A prescribed remedy must not assume its own tool exists (`prescribed-remedy-must-not-assume-its-own-tool-exists`)
- ccmemory v0.13.0 -> v0.13.1. `SESSION_PROTOCOL` (injected by the SessionStart hook) gained handling for "`memory_list` is not in your tool list": bare imperative "Call `ToolSearch("select:mcp__ccmemory__memory_list")` once to try to pull in a late-connecting server." `ToolSearch` exists only with tool-search enabled; on a gemma-4-26B session the model searched its list for `ToolSearch`, re-read it, then burned a turn on a `Bash` call whose body was its reasoning pasted as `#` comments.
- Still progress: v0.13.0 targeted SILENT failure (no ccmemory reads exactly like no memory, so the model concludes falsely "no prior memory"); that hole closed. Regression: "silently wrong" became "visibly stuck". Don't let either discredit or excuse the other.
- Rule for any injected "call tool X": (1) gate it: "IF, and only if, X is in your tool list"; (2) say X's absence is NORMAL and to SKIP, not hunt; (3) forbid the shell fallback by name (no shell path registers an MCP tool); (4) make the terminal state reachable from EVERY branch (v0.13.0's "If still unavailable, STOP" hung off the ToolSearch branch, so no-ToolSearch had no exit). Write for the least capable model that will read it (including `instenv.prompt` fan-outs).
