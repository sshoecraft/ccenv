Topic: how a ccloop session ends or relays and how that went wrong: Stop-hook semantics, the halt sentinel, background-task liveness, orphaned child processes, the context-wall signal, and why the token cutoff is not the guarantee.

## Stop hook semantics in ccloop
- Plain Claude Code: a Stop hook returning 0 with no output is a benign no-op. In ccloop the runner drives the session (on stop it summarizes the transcript and relays to a fresh session), so `return 0` lets the session END, loses the running background task's context, and short-circuits later gates in `keepgoing.py`, notably the cutoff gate that writes the halt sentinel the interactive watcher polls. [[ccloop-stop-hook-return-0-kills-session]]
- Incident: the "background-work wait gate" did `return 0` on a pending `*.output` file. Stale `.output` at relay boundary -> wait gate fired -> cutoff gate (line ~316) never ran -> `halt-<sid>` never written -> watcher never SIGTERMed the TUI -> session hung at 270k/250k tokens; user saw "I'm at the relay boundary — wrapping up." then nothing. The user had earlier pushed for "just a fucking no-op", right for pure Claude Code, wrong for ccloop; should have been caught at design time. [[ccloop-stop-hook-return-0-kills-session]]
- Rules: a gate that wants to "do nothing" while keeping the session alive MUST emit `decision: block` (re-feed), not `return 0`. Cutoff MUST come BEFORE the wait gate (losing a task to relay is recoverable; blowing past the context wall is not). [[ccloop-stop-hook-return-0-kills-session]]
- CORRECTED 2026-06-16: the earlier claim that file-presence is fine as a wait-gate trigger (stale `.output` reaped in seconds) is WRONG; see the next section and `claude-code-does-not-reap-task-output-files`. [[ccloop-stop-hook-return-0-kills-session]]
- Wait re-feeds do NOT bump the keepgoing counter or count toward `CCLOOP_MAX_CONTINUES` (that cap breaks model spin loops, not external waits). Reason text minimal ("Wait. Background command still running."), not keepgoing CONTINUE_MSG, which pushes "pick a new angle". Guarding tests: `test_cutoff_wins_over_pending_background`, `test_pending_background_blocks_with_wait_message`, `test_pending_background_does_not_bump_keepgoing_counter`. Related `no-git-checkout-to-undo-own-edits` (same session of mistakes). [[ccloop-stop-hook-return-0-kills-session]]

## Claude Code does not reap background task .output files
- Confirmed 2026-06-16 on Linux (uid 1000): Claude Code stores each Bash-background task's output at `/tmp/claude-<uid>/<slug>/<session-id>/tasks/<task-id>.output` and does NOT delete it when the command completes; it lingers for the whole session and beyond (old mxfs sessions held 7 and 41 stale files; a 5-file session matched 5 long-finished task IDs). No on-disk running-state registry exists (tasks dir holds only `.output` files). Running vs finished is writer liveness: running -> file held open by a live process (a `/proc/<pid>/fd/<n>` symlink target; live = holders > 0); finished -> 0 holders, file persists. `claude-code-does-not-reap-task-output-files`
- Impact: `keepgoing._pending_background_task_count` counted bare presence on the false belief "the harness reaps the file in seconds", so once any background command had run, its orphaned `.output` re-fired the gate on every Stop; the session could neither relay nor exit, emitting "N background command(s) still running" forever until the context wall. Seen in the mxfs run (session c3bb9e30, 5 dead files). `claude-code-does-not-reap-task-output-files`
- Fix (ccloop 0.5.1): count an `.output` only when a live process holds it open: `/proc/<pid>/fd` scan, no subprocess, only on Stop, short-circuited. Non-procfs platforms (macOS) fall back to an mtime freshness window (`STALE_OUTPUT_SECONDS=90`). Verified on the real wedged session: 5 files present -> 0 counted. Any tool asking whether a Bash background task is still running must check writer liveness (procfs fd holder or mtime), never presence. Corrects the "false positives are momentary / recoverable" claim in `ccloop-stop-hook-return-0-kills-session`. `claude-code-does-not-reap-task-output-files`

## keepgoing return 0 permits a stop, never ends an interactive TUI (fixed ccenv 0.34.1)
- Headless `-p`: a permitted stop exits the process. Interactive TUI: returns to prompt, stays resident; the only terminator is the watcher in `runner.run_session_interactive` seeing `<run-dir>/halt-<session_id>`. Any `return 0` in `keepgoing` that does not write the sentinel leaves an interactive session alive forever. [[allowing-a-stop-does-not-end-an-interactive-session]]
- Defect: `if _criteria_met(run_dir): return 0` sat ABOVE the cutoff gate (`cutoff = _read_cutoff(run_dir)`; `if cutoff > 0 and tokens >= cutoff: _signal_halt(...)`, the only sentinel writer). Once `criteria-met` was YES the sentinel was unreachable: a run met criteria at 11:39, session still resident and idle at 18:16, 510k tokens past a 500k cutoff. Both completion paths now call `_signal_converged()` first, logging `converged` not `halt`. [[allowing-a-stop-does-not-end-an-interactive-session]]
- Two cutoff paths: `hook-events.log` `fired <tokens> <sid>` comes from guard.py (PostToolUse), which detects the crossing but cannot terminate; `keepgoing` writes `halt`/`converged`. Repeated `fired` with no `halt` looks like "cutoff works but is ignored". [[allowing-a-stop-does-not-end-an-interactive-session]]
- Diagnostic lessons: verify liveness, never infer it (wrongly concluded the parent exited from 0-byte `sessions.log`; it was alive 3h29m; `ps -o pid,etime,cmd -C ccloop` should be the FIRST call). Check log field shapes against the writer (`fired` 3 fields vs `_signal_halt`'s `halt` 4 fields named a different writer, `guard`). Tests can encode the defect: two tests asserted the sentinel ABSENT after completion and passed while the bug lived; honest assertion is sentinel present and event `converged`. [[allowing-a-stop-does-not-end-an-interactive-session]]
- Campaign criteria that can never be met ("pick the highest-severity open defect ... and move to the next one") make any `criteria-met=YES` a misjudgment; before 0.34.1 a silent park, now a clean early exit; a run ending early warrants checking for `criteria-met` reappearing. [[allowing-a-stop-does-not-end-an-interactive-session]]

## Orphaned claude processes on relay: two mechanisms
- Independent; fixing the first did not fix the second. [[ccloop-interactive-relay-orphans-child-processes]]
- Mechanism 1 (bundle v0.6.1): ccloop itself dies abnormally (crash, `kill -9`, OOM); `run_session_interactive()` used plain `Popen`, child reparented to init. Fix `_pdeathsig_preexec`: `prctl(PR_SET_PDEATHSIG, SIGTERM)` via `preexec_fn` on `run_session()` and `run_session_interactive()`; chosen over `killpg` because setsid/pgid changes cost the TUI its controlling terminal (raw mode, Ctrl-C, SIGWINCH). Limit: protects only the tracked child; cleared on fork, so a wrapper's children never inherit it. [[ccloop-interactive-relay-orphans-child-processes]]
- Mechanism 2 (bundle v0.11.1 / ccloop 0.10.1), with ccloop healthy: `CCLOOP_CLAUDE_BIN` is often a shell wrapper, e.g. `/usr/local/bin/clyde` (exports `ANTHROPIC_BASE_URL`/`ANTHROPIC_MODEL`/`CLAUDE_CODE_MAX_CONTEXT_TOKENS`, runs `claude --dangerously-skip-permissions --effort medium "$@"`). Tracked PID is bash; claude is the grandchild. Relay `proc.terminate()` SIGTERMs bash; a non-interactive bash does not forward SIGTERM to its foreground job; claude is reparented (to `systemd --user`, a subreaper, not always PID 1) and runs forever, one leak per relay. [[ccloop-interactive-relay-orphans-child-processes]]
- Evidence (2026-07-24, atrader): one `ccloop --resume-run` with FOUR live `claude ... begin` processes, sessions 10/11/12/13, elapsed 3h17m/2h50m/1h21m/47m; 10-12 had `PPID 3043` (`systemd --user`) and no wrapper; 13 was the live `clyde`(bash)->`claude` pair. itrader on the same box invoked `claude` directly: one claude, PPID = ccloop. [[ccloop-interactive-relay-orphans-child-processes]]
- 30-second repro:
```
printf '#!/bin/bash\npython3 -c "import time; time.sleep(60)"\n' > w.sh
chmod +x w.sh; ./w.sh & W=$!; sleep 1; K=$(pgrep -P $W)
kill -TERM $W; sleep 1; ps -p $K -o pid=,ppid=      # -> alive, PPID 1
```
  [[ccloop-interactive-relay-orphans-child-processes]]
- Fix in `runner.py`: `_descendants()` walks `/proc` for the whole subtree deepest-first, snapshotted BEFORE signalling; `_terminate_tree()` escalates SIGTERM -> SIGKILL; each PID pinned to its `/proc/<pid>/stat` start time (`_proc_identity`) so a recycled PID is never signalled; called from the watcher on relay and swept again after `proc.wait()`. Headless `run_session()` uses `start_new_session=True` + `os.killpg` (covers wrappers); interactive cannot (setsid detaches the TUI's terminal; shared pgid means killpg would kill ccloop). [[ccloop-interactive-relay-orphans-child-processes]]
- CORRECTION: an earlier investigation ran real `claude` via `CCLOOP_CLAUDE_BIN=clyde` through 5 relays, saw `exit=143`, concluded "0/5 leaked". Wrong: 143 = SIGTERM is the wrapper bash's exit; it confirmed the tracked PID died, not that a grandchild survived. A check satisfiable by the wrong process proves nothing; assert on the PID that must NOT survive (`pgrep -P <wrapper>` before the kill). [[ccloop-interactive-relay-orphans-child-processes]]
- Testing: `tests/test_runner.py::test_interactive_relay_kills_claude_behind_a_shell_wrapper` uses a real bash wrapper and real fork/exec, finds the worker via `pgrep -P` (not the runner's own `/proc` walk). `run_session_interactive` calls `signal.signal`, so it must run on the main thread; observer/trigger go in the helper thread. Autouse `no_sleep` patches `runner.time.sleep` (the global `time` module), so waits need a `time.monotonic()` deadline (a counted retry loop waits zero; this flaked the PDEATHSIG test, fixed). `/proc/<pid>` existence is not liveness (zombie); check state `Z` (`_gone()`). [[ccloop-interactive-relay-orphans-child-processes]]
- Not applied (user-side): make the wrapper's last line `exec claude ...` so one PID gets PDEATHSIG and `terminate()`; per-wrapper, ccloop cannot rely on it, hence the tree kill. [[ccloop-interactive-relay-orphans-child-processes]]

## Context wall signal
- With auto-compact disabled (ccloop always sets `DISABLE_AUTO_COMPACT=1`) a full context makes Claude Code inject a synthetic assistant turn into the transcript JSONL and idle on "Context limit reached · /compact or /clear to continue"; with no human it wedges forever. [[context-wall-deterministic-signal]]
- Event: `{"type":"assistant","isApiErrorMessage":true,"message":{"role":"assistant","model":"<synthetic>","content":[{"type":"text","text":"Prompt is too long"}]}}`. Match `type=="assistant"` AND `isApiErrorMessage==true` AND text contains "Prompt is too long". Its `usage` is all zeros, so a naive "last assistant usage" reader reports 0 tokens for a wedged session; skip `isApiErrorMessage` turns. [[context-wall-deterministic-signal]]
- This event, not a token estimate, is the reliable full-context signal. ccloop v0.6.0: `transcript.hit_context_wall()` (tail-scan), interactive watcher relays on it, headless `-p` relays on stream `saw_prompt_too_long` after real work (aborts only with zero real turns = handoff prompt itself too big). Verified on a real wedged run: detector True, assistant_turns=100, context_tokens=172438 of 200000 (~86%). [[context-wall-deterministic-signal]]

## Relay is event-driven, the cutoff is only an early-relay knob
- ccloop's purpose: when context fills, summarize and restart fresh. The token `cutoff` (`<run-dir>/cutoff`, default 250k) is an absolute count unrelated to the model's real window; it is only an EARLY relay knob and must never be the sole guard against the hard wall. `ccloop-relay-not-cutoff-dependent`
- Why: a real run wedged on the 200K wall with `cutoff=500000` (2.5x the window, set deliberately as a test); `tokens >= cutoff` could never trip below the wall. Compounded by the old shared `/tmp/ccusage-<uid>.json` cache clobbered by a concurrent same-UID session (foreign `session_id` -> `exact_tokens` None -> gate fail-open). Either alone guarantees the wedge. `ccloop-relay-not-cutoff-dependent`
- Rule: the hard guarantee is the deterministic wall event (`runner` + `transcript.hit_context_wall`), independent of cutoff and cache. Do NOT add another magic threshold (e.g. "relay at 85% of window"); the user explicitly rejected replacing one hand-set number with another. `ccloop-relay-not-cutoff-dependent`
- Cache redesign (ccusage v0.3.0, shipped in ccenv v0.2.0 with ccloop 0.6.0): per-session file `$XDG_STATE_HOME/ccusage/<session-id>.json` (default `~/.local/state/ccusage/`), pruned after 2 days, killing the concurrent-clobber fail-open. ccloop reads its own session file (legacy `/tmp` honored as transition fallback); the MCP server reads the newest file. `ccloop-relay-not-cutoff-dependent`
