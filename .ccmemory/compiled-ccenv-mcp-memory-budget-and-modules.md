## Quota: two weekly buckets, context-weighted cost (`quota-two-weekly-buckets-and-context-weighting`)
Measured from `/usage` and 2.1.239 binary, 2026-08-22. Session (5-hour) 15%; week (all models) 19%; week (Fable) 25%. CLI tracks six windows (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`, `overage`) via `GET /api/oauth/usage` (`fetchUtilization`).
- A sonnet subagent request cannot debit the Fable bucket (settles the delegation premise); Fable debits both buckets, sonnet only all-models; delegation pays until all-models binds; at measured mix Fable binds (25% vs 19%).
- `get_context_usage`/statusline expose only `five_hour` and `seven_day`; per-model windows never reach them; use `/usage`. A +50% weekly-limits promo ran through 2026-08-31, inflating headroom; don't calibrate on it.
- `/usage`: "89% of your usage was at >150k context. Longer sessions are more expensive even when cached." So mxfs cost-audit's "~4,430 Fable requests/week" and request-count shares are proxies under one context profile. Reject "every request costs the same". Delegation's real mechanism: grind output never enters parent context, lowering context growth per request and extending work inside the 500k cutoff. Write-up `/src/ccenv/docs/context-economics.md` (also: gate subagent pass-through on `agent_id` not `agent_type`; `PreToolUse` supports non-blocking `additionalContext`; a denied tool call already cost its request).

## ccmemory list budget must trim every tier (0.19.0) (`list-budget-must-trim-every-tier`)
- Failure: `memory_list` on mxfs (1,848 memories) shipped ~14.9k tokens vs a 6,000 budget while `memory_stats` said 10,490, holding zero project notes and zero compiled articles: 180 entries, all `reference`/`feedback`/`user`.
- Four defects: (1) `Store.list_all` seeded `spent` with the whole always-listed set and trimmed only the remainder; the loop broke on the first project note, so the budget capped nothing and starved other tiers. (2) `reference` in `ALWAYS_LIST_TYPES` yet `compile._select` ingested only `type='project'`: nothing could ever retire a reference memory. (3) `compiled-` articles competed with raw notes on mtime alone: 2 of 132 listed; folding retired 1,494 notes for articles then withheld. (4) `_entry_tokens` modelled `name+description+30` while the server shipped `json.dumps(indent=2)`: 1.42x undercount, inherited by `memory_stats`. Plus `count_backlog` counted every type while only `project` was actionable: backlog floor 144 vs threshold 20, nudge fired every session and could not be silenced by compacting.
- Invariants: a budget must trim every tier including the first. Keep `ALWAYS_LIST_TYPES` small, now `("user","feedback")`; `reference` is reachable by BM25. `ALWAYS_LIST_TYPES` and `compile.COMPILABLE_TYPES` must stay complementary (`test_compilable_and_always_listed_types_are_complementary`). An unsilenceable alarm is broken: count backlog only over what compile can ingest. Estimator/serializer drift silently: `test_entry_tokens_tracks_real_wire_size`.
- Method: don't trust self-reported cost (`list_tokens_actual` 10,490 vs `len(json.dumps(payload))` 14,921). Probes: `tests/measure_list_payload.py`, `tests/simulate_list_policy.py` (opens `index.db` `mode=ro`, simulates policy on real stores; surfaced defect 3). Cleared: 33 mxfs rows have frontmatter `name:` differing from filename (e.g. `feedback_commits.md` -> `name: Commits only when work is done/working`); index keys on frontmatter name and stores `path`, so `memory_get` resolves; 0 dead paths, 0 unindexed.

## ccprospect module (v0.1.0, bundle v0.8.0, built 2026-07-12) (`ccprospect-module-created`)

- Invariants: contracts IMMUTABLE (O_EXCL writes, PreToolUse guard); state = fold of append-only events.jsonl; two dimensions attention x resolution. ## MCP alwaysLoad removed in v0.13.2 (`mcp-alwaysload-blocks-startup`)
- `install.sh` set `alwaysLoad: true` on ccmemory from v0.6.0; `strip_always_load()` now deletes it. Correction 1 (2026-07-24, recorded, not acted on): it is a deadline, not a barrier. Binary 2.1.219: alwaysLoad configs are tier "regular-required", passed `Vyl(false, ...)` so blocking regardless of `MCP_CONNECTION_NONBLOCKING`, but bounded by `MCP_CONNECT_TIMEOUT_MS` (default 5000), per tier shared; on expiry logs `[MCP] ...: N/M not ready after 5000ms — proceeding; background connection continues` and starts anyway. It never guaranteed registration.
- Correction 2 (2026-07-25) forced removal: on atrader@clyde, Claude Code driving `google/gemma-4-26B-A4B-it` via an OpenAI-compatible proxy (`chatcmpl-` tool_use_ids), 172 transcripts 2026-06-29 -> 2026-07-25: broker/journal/scheduler/searxng (unset) 353-495 successful calls each; ccusage (unset) 16 sessions, 0 rejections; ccmemory (alwaysLoad true) 0 successful memory_list EVER, 122 transcripts with `No such tool available`. ccusage is the control (same bundle, installer, box, proxy, session). Not deferral: tools absent outright. Server healthy (`claude mcp list` Connected, handshake 0.18s, SessionStart hook fired in all 5 newest transcripts); the model knew `mcp__ccmemory__memory_list` from the injected prose.
- Still useful: no hook can gate on MCP status (SessionStart completes BEFORE the init event reporting `mcp_servers`; no post-connect hook phase, anthropics/claude-code#26112; scheduled/Remote Trigger sessions miss the deferred list, #41778). No load order (both tiers in one `Promise.all`; `~/.claude.json` key order irrelevant; "sentinel server loading last" impossible). Model can enumerate its MCP surface from its tool list (eager = functions, deferred = named in a system-reminder; split on `__`); `claude mcp list` is NOT in-session truth (spawns a second copy of every server). Enumeration can't detect its own incompleteness; diff against a hardcoded expected set. Setting/removing the field: no `claude mcp add` flag; `get`/`list` don't surface it; read `~/.claude.json` and rewrite via `claude mcp remove -s user <name>` + `claude mcp add-json -s user <name> '<entry>'` (add-json refuses to overwrite) rather than `json.dump` of the 256KB file.
- Lesson: a memory saying "this mechanism does not do what its name says" is a finding to ACT on; Correction 1 sat unused a day while its predicted symptom was live, and the diagnosis was re-derived badly twice.

## ccenvmcp stdlib MCP shim (2026-06-13) (`ccenvmcp-stdlib-mcp-shim`)
- `ccenvmcp/`: ~250-line stdlib-only Python 3.9+ shim of the FastMCP slice used by tools-only servers. Why: every release of the official `mcp` SDK requires Python >=3.10, locking out Debian 11 / Raspberry Pi OS, RHEL/Alma/Rocky 9, Ubuntu 20.04; it was the ONLY hard 3.9 blocker (`nats-py` >=3.7; `watchfiles>=0.21` has a 3.9 abi3 build; all packages use `from __future__ import annotations`).
- API `from ccenvmcp import FastMCP`: `FastMCP(name, instructions=...)`, `@app.tool()` sync or async, `@app.tool(name=, description=, schema=)`, `app.run()`, `await app.run_stdio_async()`. Newline-delimited JSON-RPC 2.0: initialize / notifications/initialized / tools/list / tools/call / ping.
- 3.9 pitfall (`ccenvmcp/ccenvmcp/transport.py`): never `typing.get_type_hints()` for schemas; under `from __future__ import annotations` hints like `"int | None"` raise TypeError on 3.9. The shim parses annotation text (`_token_to_schema`; `X | None`, `Optional[X]`, `list[str]`). Tests `ccenvmcp/tests/test_transport.py`.
- Consumers: ccmemory (low-level, 5 tools, explicit schema= to keep the memory_write `type` enum; `serve()` split into `build_app()`+`serve()`), ccusage (2 sync), ccteam (9 async, instructions=); `mcp` dropped, requires-python >=3.9; versions ccmemory 0.7.0, ccusage 0.2.0, ccteam 0.3.0. ccenvmcp installs FIRST via top-level install.sh and is deliberately NOT a declared dependency (local-source installs; a declared dep triggers a failing PyPI lookup). See `ccenvmcp/docs/mcp.md`, `ccmemory-debian-build-unknown-install-layout`, `no-per-component-venvs`.

## ccloop CLI flags thread as explicit params (`ccloop-cli-flags-thread-as-params`)
- Established with `--model` (ccloop 0.9.0 / bundle 0.5.0). Config is env-driven (`_config()` reads `CCLOOP_*`) but flags do NOT mutate `os.environ`: `cli.main` -> `runner.cmd_run`/`cmd_resume` -> `runner.loop(..., model=None)`, which after `cfg = _config()` does `if model: cfg["model"] = model` (flag beats `CCLOOP_MODEL`).
- Recipe for the next value flag (e.g. `--effort`): (1) `cli.py` `_extract_value_flag(argv, flag, what)` (handles `--flag=V` and `--flag V`, last wins, missing-value error); `_extract_cutoff`/`_extract_model` wrap it; validate in the wrapper (`--model` rejects empty/whitespace so `--model=` doesn't no-op via the falsy check in `_build_command`). (2) Thread through BOTH `cmd_run` and `--resume-run`'s `cmd_resume`. (3) Update USAGE (Options plus the env var line "(--x flag wins over this)"). (4) Per-invocation like the env var: resume does NOT remember the model (unlike `--cutoff`, persisted in `<run-dir>/cutoff` because guard/keepgoing hooks in other processes read it).
- Testing: `tests/fake_claude.py` honors `FAKE_ARGS_FILE` (appends each argv as a JSON line); assert end to end, e.g. `CCLOOP_MODEL=sonnet`, pass `model="opus"`, assert `argv[argv.index("--model")+1] == "opus"`. cli parse tests stub `runner.cmd_run`/`cmd_resume` (`_stub_run`/`_stub_resume` in test_cli.py): keep signatures in sync. Never write a seam test whose fake reimplements the override logic.
