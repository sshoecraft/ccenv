Corrections from the user on how ccenv is versioned, installed and documented, plus the standing ban on git.

## Versioning

- **Bump timing** `bump-top-level-bundle-version-not-just-subdir`: bump only when a source change is about to be made, immediately before the first one in the session. A session that changes nothing bumps nothing; a write to `.ccmemory/` is not a source change. Later changes join the open version. The number moves again only to raise its size (patch -> minor -> major), never to add a step. A release seen during the session (install or push run inside it) closes that version and the next change opens a new one: 0.36.0 was installed partway through, so the installer fix after it shipped as 0.36.1. (Later superseded in wording by "one version per piece of work", but the before-first-change timing stands.)
- **What to bump**: when touching a component under `/src/ccenv` (ccloop/, ccmemory/, ccusage/, ccteam/, etc.) the component `pyproject.toml` bump is necessary but NOT sufficient. Also bump `/src/ccenv/VERSION` and add `/src/ccenv/CHANGELOG.md` entry citing the component version (e.g. "ccloop v0.5.1: ..."). The user installs the bundle, not subdirs; a component-only bump leaves the shipped artifact unversioned. User corrected this repeatedly ("you keep doing this").
- **Why up front**: the old note said "after editing any component, do BOTH bumps in the same change", plus the old CLAUDE.md line "the version is revved as part of the change", gave seven bumps in one bug-fixing session before any release. Bumping at release was rejected: Claude cannot see a release, so an outside install would ship changed code under an already-released number. Decided 2026-09-19. Relates to `ccenv-installed-vs-source-version`.
- **No hardcoded `__version__`** `version-must-have-one-source-of-truth`: `__init__.py` had hardcoded versions while `pyproject.toml` held the real one. Drift: ccloop `--version` printed 0.10.1 vs installed 0.12.0; ccmemory 0.15.0 vs 0.17.0. Caught only by running `ccloop --version` to confirm an install; a stale version reads as "the install failed" and sends you debugging a deploy that succeeded. Fix (v0.20.1, applied to ccloop, ccmemory and ccenvmcp, the last had not drifted but was fixed anyway because the defect is the duplicated source of truth):
  ```python
  from importlib.metadata import PackageNotFoundError, version as _dist_version
  try:
      __version__ = _dist_version("<pkg>")
  except PackageNotFoundError:
      __version__ = "0+unknown"
  ```
  `importlib.metadata` is stdlib from 3.8, fine under ccenvmcp's 3.9 floor, no dependency. Consequence: `--version` reports what is installed, not the source tree; they differ until reinstall (see `ccenv-installed-vs-source-version`).
  - Tautological test: `from ccloop import __version__; assert __version__ in capsys.readouterr().out` passes at any drift. A test whose expected value derives from the thing under test verifies plumbing, not correctness. Replaced by: `__init__.py` must not hardcode a version (regex on source), and `__version__` must equal `importlib.metadata.version(pkg)`.
  - Generalization: same class as the ccmemory listing budget (estimator drifted from the serializer it models) and ccloop handoff staleness. Any value hand-maintained in a second place drifts silently. Ask "how many places carry this number", not "is this number right".
- **Version history goes in CHANGELOG.md, never CLAUDE.md** `no-version-history-in-claude-md`: `ccmemory/CLAUDE.md` had a 90-line "Architecture history" listing v0.1.0 to v0.9.0. User: "why is history being kept in CLAUDE.md in _any_ project versus CHANGELOG.md???" Directed that all module-level CLAUDE.md files be cleared of history and removed entirely (architecture duplicated README.md; only unique content was the changelog). CLAUDE.md loads every session start, so history is pure overhead. Never add "## Architecture history" / "## Version history" / "## Changelog" to any CLAUDE.md. Entries go in `CHANGELOG.md` (`## vX.Y.Z`, newest first). Per-module CLAUDE.md files are deprecated; top-level `/src/ccenv/CLAUDE.md` is the global-rules file installed to `~/.claude/CLAUDE.md`; subdir architecture/install/test info goes in that subdir's `README.md`. About to write "this version did X, next added Y" outside CHANGELOG.md or a commit message: stop. Related: `ccenv-installed-vs-source-version`.

## Install design

- **Install never writes to the source tree** `install-never-writes-to-source-tree`: never design `install.sh` to write into the source tree (e.g. a `RELEASED` marker next to `VERSION`). User: "NO NO AND NO! app user or NO user should be able 'write' to this dir!! ... remember some users git clone trader then ./install.sh". The user codes as `steve` and installs as the application user; `~/.config/ccenv/installed-version` is in the installer's home, invisible to a steve session. Others install from their own clone. So Claude cannot detect a release; anything needed "at release" must happen before it, hence bump before first change.
- **No per-component venvs** `no-per-component-venvs`: do not recommend a venv per component (old ccloop README: `python3 -m venv ~/.venvs/ccloop && pip install .` plus PATH symlink). User: "we'd have a venv for EACH component of this repo?" Standard: `pip3 install --user .`, with `pipx install .` as PEP 668 fallback for a manual single-component install only. Five venvs = 5x disk for shared deps (mcp, anyio, pydantic), five symlink chains, inconsistent layouts, no isolation needed (same user, same `claude` CLI). Top-level install.sh installs all five with `pip install --user` into ONE shared site so the `ccenvmcp` shim is importable across ccmemory/ccusage/ccteam; pipx per-app venvs would break that (v0.4.1). It does NOT fall back to pipx. On PEP 668 (`error: externally-managed-environment`, `set -e` aborts) it probes the `EXTERNALLY-MANAGED` marker (`sysconfig.get_path("stdlib")`) and, only when present AND pip supports it, exports `PIP_BREAK_SYSTEM_PACKAGES=1` for its subshell. Safe: everything is `--user` into `~/.local`. Manual unblock: `PIP_BREAK_SYSTEM_PACKAGES=1 ./install.sh`. Never write per-component manual-venv recipes or convert install.sh to pipx. See `shared-userbase-compiled-dep-abi-mismatch`, `pythonuserbase-in-zshenv`.
- **`~/.claude/CLAUDE.md` ownership** `install-claude-md-component-owned` (set 2026-06-13 at user's direction): top-level `install.sh` assembles ONLY the base (bundled `CLAUDE.md` plus user/system overlays) FIRST, before any component installer (`assemble_ccenv_base_claude_md`), inside `# [CCENV MANAGED]` ... `# [/CCENV MANAGED]`. Re-run refreshes only that region (awk strips old block, regenerates, preserves outside): idempotent, no backup churn. Each component owns and appends its own section after it (e.g. `ccproject/install.sh` step 4 manages the `# [AWARENESS PROTOCOL]` marker from its own `global-claude-md-snippet.md`). Top-level never reaches into component CLAUDE.md content. `CCPROJECT_SKIP_GLOBAL_CLAUDE_MD` was REMOVED; never reintroduce a skip gate. Why: the old design pulled `ccproject/global-claude-md-snippet.md`, ran ccproject early with a SKIP gate and assembled the global file last (line ~472) while the consumer ran at ~293, causing a false "Global CLAUDE.md missing awareness protocol" verify failure. User: "submodules can install/update global CLAUDE.md as they wish ... installer should not install submodule CLAUDE.md changes." New components get their own marker-delimited idempotent self-install; do not re-centralize. Same spirit as `mcp-heal-stale-command-pattern`; related `no-per-component-venvs`.

## git

`no-git-checkout-to-undo-own-edits`: the CLAUDE.md git ban is absolute, every subcommand including read-only (`git status`, `diff`, `log`, `reflog`). Two violations: (1) undoing own edits with `git checkout -- <file>` / `git restore`: use Edit/Write to restore, or ask the user if prior content is not in context; the tree is shared, "only affected my changes" is luck. (2) "read-only verification": use Read/find/wc/grep, or ask what is uncommitted. Git is too blunt and side-effecting (index state, pagers, hooks, lockfiles). Implicit permission only from the user's words ("commit and push" allows the commit pipeline; "what's the git status" allows `git status`). When in doubt, ask first, run never.
